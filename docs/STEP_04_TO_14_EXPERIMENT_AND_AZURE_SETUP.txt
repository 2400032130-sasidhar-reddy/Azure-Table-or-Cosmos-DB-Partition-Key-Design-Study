1. PURPOSE OF THIS DOCUMENT
================================================================================

This document records the implementation and experimental workflow used for
Steps 04–14 of the Azure Cosmos DB Partition Key Design Study.

It also provides a reproducible Azure Cosmos DB setup procedure for team
members who need to recreate the experimental environment.

The project studies how partition-key design affects workload distribution,
resource consumption, latency, and the risk of hot partitions.

2. EXPERIMENTAL APPLICATION
================================================================================

PhishGuard AI is used as the realistic application workload source.

PhishGuard AI is a phishing URL detection application that processes URLs and
stores scan results.

Relevant Cosmos DB document fields include:

    userId
    url
    verdict
    confidenceScore
    riskBand
    country
    explanation
    scannedAt

The purpose of using PhishGuard AI is to obtain realistic data and access
patterns instead of relying only on an artificial database workload.

The primary subject of this project remains Cosmos DB partition-key design.

11. STEP 09 — SKEWED / HOT WORKLOAD EXPERIMENT
================================================================================

Script:

    hot_workload.py

The workload was intentionally skewed.

Total requests:

    500

Requests directed to user-001:

    400

Requests directed to other users:

    100

Therefore:

    user-001 = 80% of total requests


Observed results:

    Total requests : 500
    Successful     : 500
    Throttled      : 0
    Other errors   : 0
    Average latency: 51.34 ms
    Average RU     : 3.09 RU/request


================================================================================
12. STEP 09 — REQUEST DISTRIBUTION
================================================================================

The skewed experiment produced the following major distribution:

    user-001 : 400 requests
    Other users: 100 requests

Therefore:

    user-001 received 80% of all requests.


IMPORTANT INTERPRETATION:

This demonstrates severe workload skew toward a single logical partition
key value.

It does NOT by itself prove physical hot-partition contention.


================================================================================
13. HOT PARTITION ANALYSIS
================================================================================

Workload skew:

    A disproportionate amount of traffic is directed toward one partition-key
    value.

Hot logical partition:

    A logical partition receiving disproportionately high workload.

Physical hot-partition contention:

    Requires evidence that the workload is creating contention at the
    physical-partition level.

HTTP 429:

    Indicates that the available throughput was insufficient to immediately
    serve a request.

RU:

    RU/s represents provisioned throughput capacity.

RU/request:

    Represents the resource charge of an individual database operation.


IMPORTANT:

    Workload skew
    !=
    Hot physical partition
    !=
    Throttling


The terms are related but should not be treated as interchangeable.


================================================================================
14. EXPERIMENTAL FINDING
================================================================================

The skewed experiment demonstrated:

    80% of requests -> user-001

However:

    500 total requests
    500 successful
    0 throttled

Therefore, the correct engineering conclusion is:

"The experiment demonstrated severe workload skew toward a single logical
partition. However, under the tested 500-request workload and configured
throughput, no throttling occurred, so physical hot-partition contention was
not conclusively demonstrated."


A lower average latency in the skewed experiment should NOT be interpreted as
evidence that workload skew improves performance.

Latency can vary between experiment runs because of multiple environmental
and execution factors.


================================================================================
15. STEP 10 — IDENTIFY THE BOTTLENECK
================================================================================

A bottleneck is a component whose available capacity limits the workload.

Conceptually:

    Increasing workload
            |
            v
    Increasing resource demand
            |
            v
    Available throughput becomes limiting
            |
            v
    Increased latency / throttling risk


The current 500-request experiment did not exhaust the configured throughput.


================================================================================
16. STEP 11 — CONTROLLED STRESS TEST
================================================================================

The next experiment should progressively increase workload.

Recommended sequence:

    500 requests
        |
    1000 requests
        |
    2000 requests
        |
    Higher levels if required

Maintain approximately:

    80% -> user-001
    20% -> other users


Measure at every workload level:

    Average latency
    RU/request
    Successful requests
    HTTP 429 responses
    Request distribution
    Throughput behavior


The purpose is to determine whether increased demand produces measurable
contention or throttling.

================================================================================
18. STEP 13 — ENGINEERING DECISION
================================================================================

The partition-key decision should be based on measured evidence.

Decision workflow:

    Access Pattern
          |
          v
    Candidate Key
          |
          v
    Data Distribution
          |
          v
    Workload Distribution
          |
          v
    Controlled Load
          |
          v
    Latency / RU / 429
          |
          v
    Partition-Key Evaluation


Changing a partition key is not an ordinary runtime configuration change.

The partition-key path is defined as part of the container design.

If a different partition-key design is required, a new container and data
migration/re-ingestion may be necessary.


================================================================================
19. STEP 14 — FINAL ENGINEERING CONCLUSION
================================================================================

The study follows a measurement-driven approach to partition-key design.

We are not selecting a partition key based on theory alone.

Instead, the design is evaluated using:

    Realistic application data
          |
    Real application access patterns
          |
    Candidate partition keys
          |
    Controlled workloads
          |
    Performance measurements
          |
    Stress testing
          |
    Engineering decision


FINAL CONCLUSION:

"We are not selecting a partition key based on theory alone; we are
validating the design using realistic workloads, controlled stress testing,
and measurable performance data."
